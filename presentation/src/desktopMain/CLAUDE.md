# :presentation — desktopMain

The desktop shell, called by `:app:desktop`.

- `desktopMain/ui/CampfireDesktopApp.kt` — `CampfireDesktopApp()` hosts `CampfireApp` inside a `dragAndDropTarget` that accepts dropped files (a folder standing for the files directly inside it); a drop whose file list cannot be read is refused rather than thrown, since an exception out of the target skips the end of the drag session and the window would refuse every drag after it; links open through `java.awt.Desktop`, or through the system's own command (`open`, `rundll32`, `xdg-open`) where AWT has no desktop or its `browse` fails, and a link nothing would open is answered with a snackbar naming the address (`Message.LinkNotOpened`). That opener (`openUrl`, in `desktopMain/ui/platform/SystemBrowser.desktop.kt`) is also a Koin definition, `DesktopSystemBrowser`, the `SystemBrowser` the sync authorizer opens the consent page with, so the consent page and the links in Settings take exactly the same path. `CampfireViewModel.handleKeyEvent(...)` is wired into the window's `onKeyEvent` by `:app:desktop`: desktop has no back gesture, so Escape dismisses whatever is open on top of the app, closes the search of the screen that is on top (`CampfireViewModel.currentSearch`), pops the back stack, or — with nothing left to go back from — asks whether to close the app (`DialogType.ConfirmExit`, `CampfireViewModel.confirmExit`; Close goes on through `requestExit`), since an Escape too many is a habit of the hand rather than a decision; the window's close button and the system's quit, which are, close without asking. Which keys are shortcuts at all is decided for both the desktop and the web by one common, tested table
  (`ui/AppShortcuts.kt`: `appShortcutOf`, then `perform`), each shell only naming its keys. The same handler answers Ctrl / Cmd + F with `CampfireViewModel.openCurrentSearch`, which opens the search of the list screen on top, or gives an open one the caret back with its text selected (`SearchState.openOrFocus`), and leaves the key alone under a dialog, a sheet or a menu: nothing on a list screen is focused while its search is closed, so a shortcut inside the composition would never hear it. Ctrl / Cmd + plus (or equals), minus and zero, the shortcuts a browser zooms a page with, step the text size of the song details screen and reset it (`CampfireViewModel.zoomSongText`), under the same conditions (`isSongTextZoomable`). Only the first press of a held Escape counts: the window's preview key handler (`handlePreviewKeyEvent`) swallows the repeats AWT sends while the key stays down, which would otherwise have closed every screen and then the app. The search comes before the back stack, and not only because closing it is the smaller step: selecting a tab rebuilds the stack around it, so the setlists screen is reached with the songs screen still under it and every Escape there would otherwise leave the tab with the search still open behind it. What is open on top is `visibleDialog` plus `overlayState.isAnyMenuOpen` (`components/OverlayState.kt`, the view model's own, which `CampfireApp` provides to every `OverflowMenu` as `LocalOverlayState`): a window key handler runs before Compose turns Escape into a back event, so an Escape consumed here would pop the back stack behind a dialog, a sheet or a menu instead of closing it. The import's progress dialog is neither, so while it would be shown (`importProgress` set and no `importReport`) Escape is consumed and does nothing: it would otherwise go back behind the dialog or offer to close the app midway through the import.
