# :presentation

The entire UI: all Compose components, plus the thin per-platform shells the `:app:*` modules call into. A single Kotlin Multiplatform module (`campfire-compose-library`) — `commonMain` must stay free of JVM-only APIs (`java.*`, `KoinJavaComponent`); use `kotlin.uuid.Uuid`, `androidx.compose.ui.text.intl.Locale` and `KoinPlatform.getKoin()` instead (`desktopMain` may use `java.*`). Depends on `:domain:api` and `:chordpro` (the song model it renders) — never on repositories or local sources. Koin wiring in `Module.kt` (`presentationModule`) — `CampfireViewModel` via an explicit `viewModel { }` with named arguments (Koin's reified `viewModelOf` overloads stop at twenty-two parameters, and the constructor is past that), obtained in Compose with `koinViewModel()`.

The platform shells all live in the `ui` package next to `CampfireApp`, one per platform source set. They exist only to do what Compose cannot do in common code; anything non-trivial belongs in `commonMain` (platform-specific behavior such as scrollbars is done there with `expect`/`actual`, see `ui/platform/Platform.kt`). Each of them provides `LocalFilePicker` and passes on a `Flow` of files the operating system handed over ("open with", a share, a drop).

- `androidMain/ui/CampfireAndroidApp.kt` — `CampfireAndroidApp(urlOpener, filesToImport)` obtains the `CampfireViewModel` with `koinViewModel()`, keeps the system bar icon colors in sync with the selected theme via `enableEdgeToEdge(...)` (the app theme may differ from the system theme), and hands off to the shared `CampfireApp`. The `urlOpener` receives whether the dark theme is active so Custom Tabs can match.
- `desktopMain/ui/CampfireDesktopApp.kt` — `CampfireDesktopApp()` hosts `CampfireApp` inside a `dragAndDropTarget` that accepts dropped files; links open through `java.awt.Desktop`. `CampfireViewModel.handleKeyEvent(...)` is wired into the window's `onKeyEvent` by `:app:desktop`: desktop has no back gesture, so Escape dismisses the visible modal, pops the back stack, clears the Songs search query on the root screen, or closes the app.
- `iosMain/ui/CampfireIosApp.kt` — `CampfireIosApp(urlOpener, filePicker, filesToImport)` hosts `CampfireApp`. Takes the URL opener and the file picker as parameters so the module stays free of UIKit. Back navigation (including the swipe back gesture) is handled by Navigation 3 in `CampfireApp`.
- `wasmJsMain/ui/CampfireWebApp.kt` — `CampfireWebApp()` hosts `CampfireApp`; links open in a new tab and files dropped anywhere on the page are imported.

Everything else is `commonMain`:

- `ui/CampfireViewModel.kt` — a lifecycle `ViewModel`. Exposes `StateFlow`s derived from `GetScreenDataUseCase` (`stateIn(viewModelScope, WhileSubscribed)`), the grouped song list (`songGroups`, section headers computed here so the UI never needs `NormalizeTextUseCase`), `setlistsWithSongs`, `visibleDialog`, and the Navigation 3 `backStack` (`SnapshotStateList<CampfireDestination>`). The theme and the language come from a separate `GetUserPreferencesUseCase` rather than from `ScreenData`, so they reach the screen without waiting for the library scan. Intent handlers are non-suspend and launch in `viewModelScope`. Every entry reports `transition.isRunning` through `ReportNavigationTransition`; a back stack change that interrupts a running transition bumps `navigationGeneration`, which goes into the entry metadata so the new scene never equals the one the transition started from. Without this, reversing an in-flight transition (e.g. going back right after opening a song) sends Navigation 3 down its "predictive back cancelled" path, which cannot handle an interrupted animation and leaves the UI stuck halfway.
- `ui/CampfireApp.kt` — the root composable used by every platform shell: theme, language preference, adaptive chrome (`NavigationBar` under 600dp, `NavigationRail` above — see `components/WindowSize`; the filter side panel is decided by the screens themselves, see `hasRoomForSidePanel`), the `Scaffold` + `NavDisplay`, `CampfireDialogs`, the snackbars for import and export results, and the collection of `filesToImport`. It also rescans the library when the app is resumed, but only where the folder is one somebody else can edit (`libraryLocation != null`, i.e. iOS and desktop): on Android the library is app-private, and on the web `ON_RESUME` fires on every tab focus while OPFS cannot change behind the app's back. All `NavDisplay` transitions are defined in this file and shared by every platform (the desktop default would be none): tab switches fade through with a small slide, pushing/popping `SongDetails` and `SongEditor` slides with a parallax (Material motion scheme springs), and `predictivePopTransitionSpec` follows the predictive back gesture (Android) / edge swipe (iOS) with linear specs. `navigationTransition` serves both `transitionSpec` and `popTransitionSpec` and decides push vs. pop from the scene depth itself: Navigation 3's own detection is wrong when a back stack change interrupts a running transition (it would animate the pop with the push spec, leaving the invisible outgoing screen covering the list and swallowing clicks for the rest of the animation). Deeper scenes get a higher z-index. The rail and bottom bar are hidden on the details and editor screens; bars and side panels animate with expand/shrink using the same spatial spec so the content reflows fluidly.
- `ui/navigation/CampfireDestination.kt` — `NavKey`s: `Songs`, `Setlists`, `Settings` (top level), `SongDetails(songFileNames, setlistFileName, initialIndex)` and `SongEditor(fileName, shouldStartInsideFirstSection)`. Top level selection resets the stack to `[Songs, tab?]` so back always returns to Songs. Songs and setlists are addressed by **file name** everywhere, which is their identity on disk.
- `ui/screens/settings/SyncSettings.kt` — the sync section of the settings screen, driven entirely by `SyncState`: an invitation to connect, or the account with what the last run did and the two things one can do about it. A build with no sync credentials has an empty `viewModel.syncProviders` and says so, rather than offering a button that cannot work. A finished run is reported as a success with the exact local date and time it happened (`kotlinx-datetime`, order and separators from a string resource so each language places them itself), never as a count of what moved.
- `ui/screens/` — one package per destination (`songs`, `setlists`, `settings`, `songDetails`, `songEditor`). Screens own their `TopAppBar` (which handles the status bar inset) and get a `contentPadding` for the bottom/horizontal insets from the outer scaffold so lists scroll edge to edge. Empty and error states are their own composables and animate in and out like everything else, so nothing appears or disappears abruptly while the library is still loading.
- `ui/components/` — Material 3 list items (`SongListItem`, `SectionHeader`, `SwitchListItem`, `CheckboxListItem`, ...), `SearchField` (`SearchBarDefaults.InputField`), `SegmentedChoice`, `SongActions` (the per-song menu: edit, add to setlist, export, share where the platform has one, delete), `ImportProgress`, `SongsControls` (sort + filters, used both as side panel and bottom sheet); `SongsControlsSidePanel` spans the full height next to the screen's app bar column (not below the bar) and handles the top inset itself. The song list has priority over the panel: `hasRoomForSidePanel` only shows it when at least three `ListColumns` columns still fit beside it (~1400dp of screen width), otherwise the same controls open in a bottom sheet from an app bar action.
- `ui/dialogs/Dialogs.kt` — `CampfireDialogs` renders whatever `visibleDialog` asks for: new song and new setlist `AlertDialog`s, rename setlist, delete song / delete setlist confirmations (the only way to delete either), and the song actions, controls, song display and setlist picker `ModalBottomSheet`s.
- `ui/theme/` — `CampfireTheme` (`MaterialExpressiveTheme`, animated light/dark switch), `CampfireColorSchemes` (orange seed palettes). Icons are XML vector drawables in `composeResources/drawable/`, loaded with `painterResource(Res.drawable.x)` and passed around as `Painter`.
- `ui/platform/Platform.kt` — `expect` declarations with one actual per platform: `isDesktopPlatform` (no pull to refresh, refresh action in the app bar instead) and `libraryLocation` (a folder path on desktop, the Files app on iOS, null where the user cannot go and look — shown in Settings and used to decide whether resuming rescans) and `canAskForDonations` (false on iOS, where App Store guideline 3.1.1 lets nothing but an in-app purchase lead to paying the developer, so the "Buy me a coffee" link in the About section only exists on Android, desktop and the web).
- `ui/platform/BackgroundSync.kt` — `SyncNotifier`, provided by each shell through `LocalSyncNotifier` the way `FilePicker` is. A sync run already outlives the screen that started it, but on a phone that is not enough: Android stops a process nobody can see and iOS suspends one, so each shell has to tell its platform that something is going on. `CampfireApp` drives it from the sync state and resolves the strings, so the notification is in the language chosen *in the app*; a notification built from Android resources would follow the system's instead. Desktop and the web provide nothing, because neither needs anything.
- `ui/platform/FilePicker.kt` — the interface every shell provides through `LocalFilePicker`: `pickFiles`, `saveFile`, and `shareFile` with `canShare` saying whether sharing is a different thing from saving on this platform (it is on Android and iOS; on desktop and the web the menu shows "Export" alone).
- `ui/components/FastScroller.kt` — the only scrollbar in the app, on the song list: a draggable thumb with a 48dp touch target that only covers the thumb (other touches reach the list) and, only while the thumb is pressed, an animated bubble with the letter of the section at the top. Scroll position is estimated from the average visible item size. Visible on every platform for as long as the list is scrollable. Programmatic scrolls bypass nested scroll, so `KeepTopAppBarInSync` (in `CampfireTopAppBar.kt`) corrects the app bar's overlap state from the list.
- `ui/theme/Language.kt` — `ApplyLanguagePreference` maps the user preference to the generated `AppLocale` and sets `currentLanguage`, which every `stringResource` call observes.
- `composeResources/values[-hu]/strings.xml` — all UI strings. The `com.hyperether.localization` Gradle plugin turns them into Kotlin string tables (`build/generated/compose/resourceGenerator/kotlin/commonCustomResClass`, package `com.pandulapeter.campfire.presentation.localization`): `StringsDefault`, `StringsHu`, `AppLocale`, `currentLanguage`, `LocalizedStrings` and the language-aware `stringResource` overloads. Adding a new `values-xx` folder needs a clean build so the plugin regenerates `AppLocale`. The plugin's `generateTranslateFile` task only declares the resources folder *path* as an input, so `build.gradle.kts` registers the `strings.xml` files as inputs too; without that, new strings render as "???" until a clean build.
- `ui/components/CampfireTopAppBar.kt` — every screen's app bar: pinned scroll behavior plus an animated shadow/tint once content scrolls underneath (screens apply `nestedScroll(scrollBehavior.nestedScrollConnection)`). The section headers of the lists are raised pills (`SectionHeader`) for the same reason. They are ordinary items that scroll away with their section; clicking one scrolls back to the start of that section (`animateScrollToKey`, which looks the header's index up by its key, since an ordinary item is not told its own).
- `screens/songDetails/SongLyrics.kt` — renders the `ChordProSong` the parser produced (sections, chorus recall, the three comment styles, tabs in a monospace font, grids, the metadata header chips). Lyrics are split into sections and flowed into columns by `SongSectionsLayout`. It uses the *fewest* (and therefore widest) columns the song still fits the screen with, so the vertical space is used and the lyrics wrap as little as possible: the candidates are evaluated from the sections' intrinsic heights (the winner is the only width they are measured at, and a candidate that does not fit jumps straight to the smallest count that could), column widths are clamped to 384–560dp scaled by `fontScale` and the block is centered. Songs that do not fit at any count get as many columns as the width allows. `SongDetailsScreen` has to pass the height available without scrolling (`availableHeight`, from a `BoxWithConstraints` around the scrolling content), since inside the `verticalScroll` the layout only sees infinite height. Sections are distributed with a dynamic program that minimizes the columns' squared deviation from the ideal height — a greedy fill leaves every column short of the target and dumps all the accumulated slack on the last one. Section headers are the same raised pills as the song lists' section headers, scrolling with their section and hanging into the left padding so their text keeps the content's keyline; choruses are drawn on a raised card instead and keep a plain label (in the pills' `primary` text color), the other sections are indented to match the card's content. Sections are never split and animate between layouts with `animateBounds` inside a `LookaheadScope`.
- `screens/songDetails/SongDisplayControls.kt` / `FontScaleGestures.kt` — the transposition and text size steppers (`fontScale` in the view model, persisted in `UserPreferences.fontScale` with a debounce because a pinch changes it every frame). Each stepper is a tonal pill (`surfaceContainerHighest`, `CircleShape`) around its two buttons and the value, so that two of them side by side still read as two controls; the app bar uses a shorter variant of it (`isCompact`, which also lowers `LocalMinimumInteractiveComponentSize` to match the smaller buttons), the sheet keeps the 48dp touch targets. Expanded windows show the steppers inline in the app bar; narrower ones get a single "display options" action that opens the `SongDisplayControls` bottom sheet, so the bar never crowds. `Modifier.fontScaleGestures` handles pinch (damped with an exponent, so it is slow and precise) and Ctrl / Cmd + scroll wheel in the initial pointer pass and consumes them, leaving one-finger scrolling and plain wheel scrolling to the content.
- `screens/songEditor/` — the raw ChordPro editor: a `BasicTextField` over a `TextFieldState` (its own `scrollState`, never wrapped in a `verticalScroll` — that swallows the press that places the caret), autosave a second after typing stops and whenever the editor leaves the screen, undo/redo from `TextFieldState.undoState`, and a live preview of the same `SongLyrics` the viewer uses, side by side on wide windows and behind an Edit / Preview toggle on narrow ones. `ChordProOutputTransformation` colours the text from `ChordProHighlighter`'s tokens in the viewer's own colours, so a chord looks like a chord on both sides of the divider.
