# :presentation

The entire UI: all Compose components, plus the thin per-platform shells the `:app:*` modules call into. A single Kotlin Multiplatform module (`campfire-compose-library`) — `commonMain` must stay free of JVM-only APIs (`java.*`, `KoinJavaComponent`); use `kotlin.uuid.Uuid`, `androidx.compose.ui.text.intl.Locale` and `KoinPlatform.getKoin()` instead (`desktopMain` may use `java.*`). Depends on `:domain:api` and `:chordpro` (the song model it renders) — never on repositories or local sources. Koin wiring in `Module.kt` (`presentationModule`) — `CampfireViewModel` via an explicit `viewModel { }` with named arguments (Koin's reified `viewModelOf` overloads stop at twenty-two parameters, and the constructor is past that), obtained in Compose with `koinViewModel()`.

The platform shells all live in the `ui` package next to `CampfireApp`, one per platform source set. They exist only to do what Compose cannot do in common code; anything non-trivial belongs in `commonMain` (platform-specific behavior such as scrollbars is done there with `expect`/`actual`, see `ui/platform/Platform.kt`). Each of them provides `LocalFilePicker` and passes on a `Flow` of files the operating system handed over ("open with", a share, a drop).

- `androidMain/ui/CampfireAndroidApp.kt` — `CampfireAndroidApp(urlOpener, filesToImport)` obtains the `CampfireViewModel` with `koinViewModel()`, keeps the system bar icon colors in sync with the selected theme via `enableEdgeToEdge(...)` (the app theme may differ from the system theme), and hands off to the shared `CampfireApp`. The `urlOpener` receives whether the dark theme is active so Custom Tabs can match. `platform/AppUpdate.android.kt` and `platform/SyncNotificationPermission.kt` are next to it, both here rather than in `:app:android` because a composable can ask for everything they need (the activity, an activity result launcher, the lifecycle) by itself. The notification permission is asked for the moment sync becomes connected — the only thing Campfire ever posts a notification for, and the first point at which the question means anything — because a foreground service started without it keeps the run alive but has its notification silently dropped, leaving a sync the user can neither follow nor stop from outside the app. A refusal costs the notification, not the sync, so the answer is ignored and never asked about again.
- `desktopMain/ui/CampfireDesktopApp.kt` — `CampfireDesktopApp()` hosts `CampfireApp` inside a `dragAndDropTarget` that accepts dropped files; links open through `java.awt.Desktop`. `CampfireViewModel.handleKeyEvent(...)` is wired into the window's `onKeyEvent` by `:app:desktop`: desktop has no back gesture, so Escape dismisses the visible modal, pops the back stack, clears the Songs search query on the root screen, or closes the app.
- `iosMain/ui/CampfireIosApp.kt` — `CampfireIosApp(urlOpener, filePicker, filesToImport)` hosts `CampfireApp`. Takes the URL opener and the file picker as parameters so the module stays free of UIKit. Back navigation (including the swipe back gesture) is handled by Navigation 3 in `CampfireApp`.
- `wasmJsMain/ui/CampfireWebApp.kt` — `CampfireWebApp()` hosts `CampfireApp`; links open in a new tab and files dropped anywhere on the page are imported.

Everything else is `commonMain`:

- `ui/CampfireViewModel.kt` — a lifecycle `ViewModel`. Exposes `StateFlow`s derived from `GetScreenDataUseCase` (`stateIn(viewModelScope, WhileSubscribed)`), the grouped song list (`songGroups`, section headers computed here so the UI never needs `NormalizeTextUseCase`), `setlistsWithSongs`, `visibleDialog`, and the Navigation 3 `backStack` (`SnapshotStateList<CampfireDestination>`). The theme and the language come from a separate `GetUserPreferencesUseCase` rather than from `ScreenData`, so they reach the screen without waiting for the library scan. Intent handlers are non-suspend and launch in `viewModelScope`; the ones that write to the library go through `launchLibraryChange`, which turns a write that failed into a `Message.OperationFailed` snackbar instead of an uncaught exception that would take the app down on Android. A state is `asEagerState` whenever its first value is acted on rather than merely shown (`syncState`, which the Android shell stops the sync service from; `allSongs`, which the details screen picks its opening page from) — a `WhileSubscribed` state hands its subscriber the initial value for one frame first. Those `asState` states forget their last value the moment they stop (`replayExpirationMillis = 0`), since the initial value is what each of them means by "nothing has been worked out yet": kept, the song list would be entered on the answer worked out before a library change its screen was away for, which is exactly what a first sync is — it fills the library from the settings screen, and the list then opened on "Your library is empty" while the settings screen next to it already counted the songs. The search and the grouping run over `searchableSongs`, the library with every title and artist normalized once, rather than normalizing per keystroke. Tagging a song (`setSongTag`) rewrites the file through `SetChordProTagUseCase` rather than touching the list entry, so the tag is in the song wherever that song goes; the tag *filter* is a user preference instead, since it is about this device's view of the library. Every entry reports `transition.isRunning` through `ReportNavigationTransition`; a back stack change that interrupts a running transition bumps `navigationGeneration`, which goes into the entry metadata so the new scene never equals the one the transition started from. Without this, reversing an in-flight transition (e.g. going back right after opening a song) sends Navigation 3 down its "predictive back cancelled" path, which cannot handle an interrupted animation and leaves the UI stuck halfway.
- `ui/CampfireApp.kt` — the root composable used by every platform shell: theme, language preference, adaptive chrome (`NavigationBar` under 600dp, `NavigationRail` above — see `components/WindowSize`; the filter side panel is decided by the screens themselves, see `hasRoomForSidePanel`), the `Scaffold` + `NavDisplay`, `CampfireDialogs`, the snackbars for import and export results (queued with a running number, because two identical results in a row are the same object and an effect keyed on the message alone would never show the second), and the collection of `filesToImport`. `SyncNotificationEffect` only ever reports "nothing to show" after it has shown something: reported on the first frame of every composition it would reach the Android shell as "stop the service" whenever the app was opened onto a run already going in the background. It also rescans the library when the app is resumed, but only where the folder is one somebody else can edit (`libraryLocation != null`, i.e. iOS and desktop): on Android the library is app-private, and on the web `ON_RESUME` fires on every tab focus while OPFS cannot change behind the app's back. All `NavDisplay` transitions are defined in this file and shared by every platform (the desktop default would be none): tab switches fade through with a small slide, pushing/popping `SongDetails` slides horizontally with a parallax (Material motion scheme springs), and `predictivePopTransitionSpec` follows the predictive back gesture (Android) / edge swipe (iOS) with linear specs. `SongEditor` is the exception and always moves vertically, up when it is opened and down however it is left, the predictive gesture included: it is presented as a modal over the song rather than as another card of the deck, which is what its Close button says as well. `CampfireDestination.SongEditor.isContentKey` is how the specs recognize it, since a scene only exposes content keys. `navigationTransition` serves both `transitionSpec` and `popTransitionSpec` and decides push vs. pop from the scene depth itself: Navigation 3's own detection is wrong when a back stack change interrupts a running transition (it would animate the pop with the push spec, leaving the invisible outgoing screen covering the list and swallowing clicks for the rest of the animation). Deeper scenes get a higher z-index. The rail and bottom bar are hidden on the details and editor screens; bars and side panels animate with expand/shrink using the same spatial spec so the content reflows fluidly. The chrome and the screens are laid out together by `NavigationChromeScaffold`, a `SubcomposeLayout` that measures the rail (or the bar) and only then composes the screens, with its thickness already known: that size is Material's to decide, and reporting it back as state from the laid out chrome arrives one layout pass too late, so the app's first frame would be composed as if the window held no chrome at all — the screens covering the rail and the lists settling their column counts for the full width, all of it laid out again a frame later. It costs no layer that was not there already, since the window size used to come through a `BoxWithConstraints`, which is the same thing. The chrome is placed under the screens and `placeRelative`d, so the rail sits on the start edge the screens are inset from. Nothing is drawn at all until the preferences have been read (`arePreferencesLoaded` — *read*, not read successfully, so a failed read opens the app in the defaults rather than never): they decide the palette and the language, and the window would otherwise open on the system's guess at both and correct itself a frame later, in an accent color and a language the user did not choose. That frame is not a fleeting one — on a cold start the second frame is several hundred milliseconds behind the first — and the wait costs nothing but the frame that would have been wrong anyway, since the window is already painted in the theme's background.
- `ui/navigation/CampfireDestination.kt` — `NavKey`s: `Songs`, `Setlists`, `Settings` (top level), `SongDetails(songFileNames, setlistFileName, initialIndex)` and `SongEditor(fileName, shouldStartInsideFirstSection)`, the last of which also answers `isContentKey` so that `CampfireApp`'s transitions can pick the editor out of a scene. Top level selection resets the stack to `[Songs, tab?]` so back always returns to Songs. Songs and setlists are addressed by **file name** everywhere, which is their identity on disk.
- `ui/screens/settings/SyncSettings.kt` — the sync section of the settings screen, driven entirely by `SyncState`: an invitation to connect, or the account with what the last run did and the two things one can do about it. A build with no sync credentials has an empty `viewModel.syncProviders` and says so, rather than offering a button that cannot work. A finished run is reported as a success with the exact local date and time it happened (`kotlinx-datetime`, order and separators from a string resource so each language places them itself), never as a count of what moved.
- **Performance mode** (`UserPreferences.isPerformanceModeEnabled`, the switch at the very top of the settings screen, above its first section heading, since it is what decides what the rest of that list is still allowed to do) is the one preference that reaches every screen rather than one of them, so `CampfireViewModel` exposes it as `isPerformanceModeEnabled` on its own and each screen collects that instead of reading it out of the preferences. It is read only mode for the app while it is being played from: the two "New" buttons, the per-song menu (and the long press that opens it on touch), the actions of a setlist header, the reordering and the swipe that removes a song from one, the "Add to setlist" action, the tag chips of the song details header and the transposition stepper all leave, which is also every way into the editor — the screen stays reachable by nothing. What is left is what a song is read with: the search, the sorting, the tag filter, the text size, lyrics only mode and the rescan, none of which change a file. The settings screen is the exception and keeps every row it has, since it is where the mode is switched back off; the two library actions there are disabled rather than hidden, the way the chord spelling is under lyrics only mode. Files the operating system hands over ("open with", a share, a drop) are still imported: that is not a tap that can happen by accident.
- `ui/screens/` — one package per destination (`songs`, `setlists`, `settings`, `songDetails`, `songEditor`). Screens own their `TopAppBar` (which handles the status bar inset) and get a `contentPadding` for the bottom/horizontal insets from the outer scaffold so lists scroll edge to edge. Empty and error states are their own composables and animate in and out like everything else, so nothing appears or disappears abruptly while the library is still loading. The song and setlist lists animate their items into place (`components/ListItemAnimation.kt`), but only once the library has arrived whole: the first read publishes what it has put together as it goes, so a list fills up in several batches and animating those would have it rearranging itself while the app is still opening. `rememberHasLoadedLibrary` is what draws that line, and it is an effect rather than `!isLoading` read directly, since the last and largest batch lands in the very composition that goes false.
- `ui/components/` — Material 3 list items (`SongListItem`, `SectionHeader`, `SwitchListItem`, `CheckboxListItem`, ...), `SearchField` (`SearchBarDefaults.InputField`), `SegmentedChoice`, `ColorChoice` (the theme colors as discs rather than as names, wrapping instead of scrolling so none of them hides behind a gesture; the two whose color is not what picks them out — the app's own and the system's — carry an icon, which the check replaces while they are selected. The selected one is ringed in its own color, because a mark in the middle of a disc is read as what that color *is* once some of them carry an icon, so the selection has to sit where an icon never can), `SongActions` (the per-song menu: edit, add to setlist, export, share where the platform has one, delete), `ImportProgress`, `SongsControls` (sort + filters, used both as side panel and bottom sheet); `SongsControlsSidePanel` spans the full height next to the screen's app bar column (not below the bar) and handles the top inset itself. The song list has priority over the panel: `hasRoomForSidePanel` only shows it when at least three `ListColumns` columns still fit beside it (~1400dp of screen width), otherwise the same controls open in a bottom sheet from an app bar action.
- `ui/components/Tags.kt` — `TagFlowRow` and `TagPill`, the one place a tag is drawn: under the artist in a song row (clipped to a single line, so a song filed under a dozen labels cannot make its row taller than the others), removable in the song details header, and as the suggestions of the tag dialog. The filter chips of `SongsControls` are Material `FilterChip`s instead, since there the selected state is the point. `TagFilters` (in `Controls.kt`) shows the most used tags first and keeps the rest behind "Show all": the set of tags is whatever the library grew, and a hundred of them must not push the sorting mode off the panel. A selected tag is always among the visible ones, and the "any / every" choice only appears once two are on, because with one it would mean the same either way.
- `ui/dialogs/Dialogs.kt` — `CampfireDialogs` renders whatever `visibleDialog` asks for: the import conflicts dialog (the names an import would land on that are already taken by something else, with keep both / replace / skip and a cancel that leaves the library untouched — one answer for the whole batch, since the batch it exists for is an archive of hundreds; the plan it answers lives in the view model, because the answer can arrive long after the screen the import was started from), new song and new setlist `AlertDialog`s, rename setlist, delete song / delete setlist confirmations (the only way to delete either), the editor's unsaved changes and revert questions, and the song actions, controls, song display and setlist picker `ModalBottomSheet`s. The setlist picker is the one sheet that stays where it is while a dialog is up: its "New setlist" action renders the naming dialog on top of it from the picker's own state rather than through `visibleDialog` (which holds one dialog at a time), because the song goes into the new setlist as soon as it exists (`createSetlistWithSong`) and the picker is where that shows. A sheet that hides itself before running an action (`sheetState.hide()`) has to clear `visibleDialog` as well: Material's `ModalBottomSheet` only calls `onDismissRequest` for a swipe, a tap on the scrim or a back press, and a hidden sheet whose state is still set keeps its invisible modal layer over the screen, swallowing the next tap.
- `ui/theme/` — `CampfireTheme` (`MaterialExpressiveTheme`), which is driven by two independent preferences: `themeColor` picks the palette and `uiMode` picks its light or dark half. A change to either cross fades every color role from the scheme currently on screen to the new one with one progress value, so an interrupted switch continues from what is visible instead of jumping back. `ColorSchemes.kt` holds the `ColorSchemePair` (a palette's two halves, which always travel together) and `themeColorOptions()`, the single ordered list both the settings screen and `colorSchemePair()` read — a color the device cannot honor is simply not in it. `CampfireColorScheme.kt` is the app's own orange, hand-saturated over Material's tonal mapping of #F57C00; `MaterialColorSchemes.kt` is the rest, seven seeds run through Material's tonal spot mapping and pasted in, so a new color is a seed rather than forty values. `DynamicColorSchemePair.kt` is the one `expect`/`actual` here: on Android 12 and above it is `dynamicLightColorScheme` / `dynamicDarkColorScheme`, everywhere else null, which is what keeps the "System" swatch off the other platforms. Icons are XML vector drawables in `composeResources/drawable/`, loaded with `painterResource(Res.drawable.x)` and passed around as `Painter`.
- `ui/platform/Platform.kt` — `expect` declarations with one actual per platform: `isDesktopPlatform` (no pull to refresh, refresh action in the app bar instead) and `libraryLocation` (a folder path on desktop, the Files app on iOS, null where the user cannot go and look — shown in Settings and used to decide whether resuming rescans) and `canAskForDonations` (false on iOS, where App Store guideline 3.1.1 lets nothing but an in-app purchase lead to paying the developer, so the "Buy me a coffee" link in the About section only exists on Android, desktop and the web).
- `ui/platform/AppUpdate.kt` / `ui/AppUpdateGate.kt` — what the store the app came from has to say about a newer build of it, which is only ever something on Android: Play is the one store of the four with an API for this (the App Store has none, and asking Apple's public lookup endpoint instead would be the second thing in the app that reaches the network). `AppUpdateGate` wraps the whole app inside `CampfireApp`, so the hint and the blocking screen are in the theme and the language chosen *in the app*. The policy is the Play release's own `updatePriority` and nothing else: 2–3 is a dismissible offer of a flexible update, 4–5 a screen the app cannot be used past. That screen is drawn *over* the app rather than in place of it, so an update that turns out not to install leaves the library where the user was. None of it shows up in a build Play did not install, which answers every check with an error. See the Updates section of the root `CLAUDE.md`.
- `ui/platform/LibraryPersistence.kt` — `requestLibraryPersistence()`, asked once from `CampfireApp` as the app starts and read back by the settings screen. Three platforms answer `GUARANTEED` without doing anything, since their library is in a file system of their own; the web actual calls `navigator.storage.persist()`, which is what stops a browser short of space from evicting the origin's storage — and with it the only copy of the user's library. The answer is cached, because the settings screen asks the same question again and the browsers that decide by asking the user must only ask once. A refusal is shown in the Library section instead of the location the other platforms have there, since a library that may be evicted is worth one line and an export.
- `ui/platform/BackgroundSync.kt` — `SyncNotifier`, provided by each shell through `LocalSyncNotifier` the way `FilePicker` is. A sync run already outlives the screen that started it, but on a phone that is not enough: Android stops a process nobody can see and iOS suspends one, so each shell has to tell its platform that something is going on. `CampfireApp` drives it from the sync state and resolves the strings, so the notification is in the language chosen *in the app*; a notification built from Android resources would follow the system's instead. Desktop and the web provide nothing, because neither needs anything.
- `ui/platform/FilePicker.kt` — the interface every shell provides through `LocalFilePicker`: `pickFiles`, `saveFile`, and `shareFile` with `canShare` saying whether sharing is a different thing from saving on this platform (it is on Android and iOS; on desktop and the web the menu shows "Export" alone).
- `ui/components/FastScroller.kt` — the only scrollbar in the app, on the song list: a draggable thumb with a 48dp touch target that only covers the thumb (other touches reach the list) and, only while the thumb is pressed, an animated bubble with the letter of the section at the top. Scroll position is estimated from the average visible item size. Visible on every platform for as long as the list is scrollable. Programmatic scrolls bypass nested scroll, so `KeepTopAppBarInSync` (in `CampfireTopAppBar.kt`) corrects the app bar's overlap state from the list.
- `ui/theme/Language.kt` — `ApplyLanguagePreference` maps the user preference to the generated `AppLocale` and sets `currentLanguage`, which every `stringResource` call observes.
- `composeResources/values[-hu]/strings.xml` — all UI strings. The `com.hyperether.localization` Gradle plugin turns them into Kotlin string tables (`build/generated/compose/resourceGenerator/kotlin/commonCustomResClass`, package `com.pandulapeter.campfire.presentation.localization`): `StringsDefault`, `StringsHu`, `AppLocale`, `currentLanguage`, `LocalizedStrings` and the language-aware `stringResource` overloads. Adding a new `values-xx` folder needs a clean build so the plugin regenerates `AppLocale`. The plugin's `generateTranslateFile` task only declares the resources folder *path* as an input, so `build.gradle.kts` registers the `strings.xml` files as inputs too; without that, new strings render as "???" until a clean build.
- `ui/components/CampfireTopAppBar.kt` — every screen's app bar: pinned scroll behavior plus an animated shadow/tint once content scrolls underneath (screens apply `nestedScroll(scrollBehavior.nestedScrollConnection)`). A screen with more controls than one row holds puts the rest in `bottomContent`, which is drawn inside the same surface (the editor's toolbar), so the whole bar tints and lifts as one. The section headers of the lists are raised pills (`SectionHeader`) for the same reason. They are ordinary items that scroll away with their section; clicking one scrolls back to the start of that section (`animateScrollToKey`, which looks the header's index up by its key, since an ordinary item is not told its own).
- `screens/songDetails/SongLyrics.kt` — renders the `ChordProSong` the parser produced (sections, chorus recall, the three comment styles, tabs in a monospace font, grids, the metadata header). Tablature is a run of lines inside a section rather than a section of its own (see `:chordpro`), so the lines of a section are grouped before they are drawn: each run of `ChordProLine.Tab` becomes one sideways scrolling block, because its columns only line up while they are measured together, and everything else is laid out line by line around it. A paragraph that holds nothing *but* one of the two still gets the default "Tab" / "Grid" heading, since that is a bare `{start_of_tab}` standing on its own and it named itself before; one with lyrics around the run is an ordinary paragraph and heading it would be a lie. Lyrics-only mode drops the tab and grid lines the way it drops the chords, since neither says anything without them, and a section left with nothing that way is dropped whole rather than leaving its heading behind. The header carries the song's tags — each removable, followed by an "Add tag" chip that opens the suggestions dialog — and then every other directive the editor can insert, since one that is written but never shown is one the user cannot check: the capo, the tempo and the time on an accent coloured line (what is read off the page while playing), the composer, lyricist, album, year and duration on a quieter one under it (what is only ever looked up). The title, the subtitle, the artist and the key are the ones that are deliberately not repeated, since the bar has all four — the subtitle in parentheses after the title (`ChordProMetadata.displayTitle`, which is how a song is named everywhere in the app), and the key inside the transposition control, which is the only reason to look at it. The editing chips are passed in and are absent in the editor's preview, where the file is under the caret and a chip writing into it from the side would be editing text that has not been saved, and in performance mode, which takes every way of writing to a file out of the app. Lyrics are split into sections and flowed into columns by `SongSectionsLayout`. It uses the *fewest* (and therefore widest) columns the song still fits the screen with, so the vertical space is used and the lyrics wrap as little as possible: the candidates are evaluated from the sections' intrinsic heights (the winner is the only width they are measured at, and a candidate that does not fit jumps straight to the smallest count that could), column widths are clamped to 384–560dp scaled by `fontScale` and the block is centered. Songs that do not fit at any count get as many columns as the width allows. `SongDetailsScreen` has to pass the height available without scrolling (`availableHeight`, from a `BoxWithConstraints` around the scrolling content), since inside the `verticalScroll` the layout only sees infinite height. Sections are distributed with a dynamic program that minimizes the columns' squared deviation from the ideal height — a greedy fill leaves every column short of the target and dumps all the accumulated slack on the last one. Section headers are the same raised pills as the song lists' section headers, scrolling with their section and hanging into the left padding so their text keeps the content's keyline; choruses are drawn on a raised card instead and keep a plain label (in the pills' `primary` text color), the other sections are indented to match the card's content. Sections are never split and animate between layouts with `animateBounds` inside a `LookaheadScope`. Two settings reach in here: `isLyricsOnlyModeEnabled` drops the chords (and with them the tab and grid sections, and the transposition control, which would have nothing left to act on), and `isHorizontalSectionFlowEnabled` fills the columns in rows across the page the way the systems of sheet music are read instead of column by column. Both apply to the editor's preview as well, since it renders the same `SongLyrics`.
- `screens/songDetails/SongDisplayControls.kt` / `FontScaleGestures.kt` — the transposition and text size steppers (`fontScale` in the view model, persisted in `UserPreferences.fontScale` with a debounce because a pinch changes it every frame). Each stepper is a tonal pill (`surfaceContainerHighest`, `CircleShape`) around its two buttons and the value, so that two of them side by side still read as two controls; the app bar uses a shorter variant of it (`isCompact`, which also lowers `LocalMinimumInteractiveComponentSize` to match the smaller buttons), the sheet keeps the 48dp touch targets. Expanded windows show the steppers inline in the app bar; narrower ones get a single "display options" action that opens the `SongDisplayControls` bottom sheet, so the bar never crowds. `Modifier.fontScaleGestures` handles pinch (damped with an exponent, so it is slow and precise) and Ctrl / Cmd + scroll wheel in the initial pointer pass and consumes them, leaving one-finger scrolling and plain wheel scrolling to the content.
- `screens/songEditor/` — the raw ChordPro editor, presented as a modal: it comes up from the bottom and its app bar starts with Close rather than Back. The whole bar is one surface (`CampfireTopAppBar`'s `bottomContent`), so everything in it tints and lifts together as the text scrolls underneath, and it is four rows deep on a narrow window:
  - the **title row**, holding what acts on the file — undo/redo from `TextFieldState.undoState`, Save, and an overflow menu;
  - a row with the **transposition stepper** and the **Edit / Preview / Split** choice. These two are together because they are the two controls here that do not write at the caret, which is why they are also the two that stay when the rest leaves. Split is only offered where two panes fit (`WindowSize.EXPANDED`) but is what the choice starts at, and a window that narrows only *shows* Edit instead of it, so widening the window again goes back to both panes. The choice is always drawn, including on a window wide enough that it has all three options, so that the stepper is never alone in a row of its own;
  - two rows of `EditorToolbar.kt`, a button for every directive `ChordProParser` understands and the app then shows, so that a format whose vocabulary only exists in its own documentation can be written without knowing it by heart. They are split into what writes what the song **is** (title, key, tempo — what a file opens with, usually filled in once) and, under it, what writes the **song** (chords, the seven sections the app has a name for, tablature and grids, comments), so the row being scrolled through is always the short one. Tab and Grid are a group of their own between the sections and the comments, because that is what they are: a display mode that opens inside a section rather than a section of its own.
  - Two kinds of directive are deliberately absent, both still read without complaint: `{new_song}`, since the editor only ever holds one song, and `{new_page}` / `{column_break}`, since Campfire flows sections into columns at whatever size the window is and a hand written break would decide nothing. The rows scroll horizontally rather than wrapping, and their buttons take no focus, or the keyboard would close under the toolbar on every tap and the insertion would land where the caret used to be. Everything in braces is inserted on a line of its own, which is the only way ChordPro reads it as a directive.
  - The stepper is the details screen's own `TextTranspositionControls`, except that transposing here rewrites the file rather than changing how it is read: there is no amount and nothing to reset to, so it shows the song's key, or a `?` where the file names none. Either a `{key}` or a chord is enough to enable it — a key says what the song is in and is worth moving before a chord has been written under it, and a chord chart with no key is still a chord chart. The title is `ChordProMetadata.displayTitle` over the text as it is typed and the line under it the artist, both from one `ChordProParser.summarize` call that also answers whether there is anything to transpose; the save state is the Save button's own enabled state and is not spelled out.
  - Export and Delete are not here: they belong to the song list and the viewer. Revert is, alone in the overflow menu and behind a confirmation (`DialogType.RevertChanges`) — a menu of one rather than a button of its own, because throwing away everything typed since the last save is not something to end up in by mistapping the button next to Save. It is answered by the screen rather than by the view model — the text goes back through the field's own editing, so a revert is one more step of the undo history instead of the end of it.
  - The screen itself is a `BasicTextField` over a `TextFieldState` (its own `scrollState`, never wrapped in a `verticalScroll` — that swallows the press that places the caret), an explicit Save action (and Ctrl / Cmd + S) which is the only thing that ever writes the file, and a live preview of the same `SongLyrics` the viewer uses, side by side where the window has the room for it and one at a time otherwise — and the insertion rows leave with the field they write into whenever the preview is the only pane showing. The text size preference reaches the preview and deliberately not the field: it is how large the lyrics are read from across a room, and the field holds the source of the file rather than the song (scaling it would also move the columns of a tab away from the width the monospaced font keeps them at). Lyrics only mode is the one preference that does not reach the preview at all: it is a way of reading a song, and a preview that hid the chords being typed opposite it would answer an edit with nothing. The two panes are `weight(1f)` and not `fillMaxSize()`: a `Column` measures a weightless child against an unbounded height, and a song longer than the screen then lays the field out past the bottom edge of it instead of scrolling inside it. `ChordProOutputTransformation` colours the text from `ChordProHighlighter`'s tokens in the viewer's own colours, so a chord looks like a chord on both sides of the divider. The screen reports the text to the view model as it is typed without saving it (`onEditorTextChanged`), which is what `hasUnsavedEditorChanges` is measured from: every way back out of a screen goes through `CampfireViewModel.navigateBack`, so that is where an editor with unsaved text is caught and the `UnsavedChanges` dialog (save / discard / cancel) is asked instead of popping. The draft is also what the dialog saves, which is why it lives in the view model rather than here - the answer can come after this screen is gone.
