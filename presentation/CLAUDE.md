# :presentation

The entire UI: all Compose components, plus the thin per-platform shells the `:app:*` modules call into. A single Kotlin Multiplatform module (`campfire-compose-library`) — `commonMain` must stay free of JVM-only APIs (`java.*`, `KoinJavaComponent`); use `kotlin.uuid.Uuid`, `androidx.compose.ui.text.intl.Locale` and `KoinPlatform.getKoin()` instead (`desktopMain` may use `java.*`). Depends on `:domain:api` and `:chordpro` (the song model it renders) — never on repositories or local sources. Koin wiring in `Module.kt` (`presentationModule`) — `CampfireViewModel` via an explicit `viewModel { }` with named arguments (Koin's reified `viewModelOf` overloads stop at twenty-two parameters, and the constructor is past that), obtained in Compose with `koinViewModel()`.

The platform shells all live in the `ui` package next to `CampfireApp`, one per platform source set. They exist only to do what Compose cannot do in common code; anything non-trivial belongs in `commonMain` (platform-specific behavior such as scrollbars is done there with `expect`/`actual`, see `ui/platform/Platform.kt`). Each of them provides `LocalFilePicker` and passes on a `Flow` of files the operating system handed over ("open with", a share, a drop).

- `androidMain/ui/CampfireAndroidApp.kt` — `CampfireAndroidApp(urlOpener, filesToImport)` obtains the `CampfireViewModel` with `koinViewModel()`, keeps the system bar icon colors in sync with the selected theme via `enableEdgeToEdge(...)` (the app theme may differ from the system theme), and hands off to the shared `CampfireApp`. The `urlOpener` receives whether the dark theme is active so Custom Tabs can match. `platform/AppUpdate.android.kt` and `platform/SyncNotificationPermission.kt` are next to it, both here rather than in `:app:android` because a composable can ask for everything they need (the activity, an activity result launcher, the lifecycle) by itself. The notification permission is asked for the moment sync becomes connected — the only thing Campfire ever posts a notification for, and the first point at which the question means anything — because a foreground service started without it keeps the run alive but has its notification silently dropped, leaving a sync the user can neither follow nor stop from outside the app. A refusal costs the notification, not the sync, so the answer is ignored and never asked about again.
- `desktopMain/ui/CampfireDesktopApp.kt` — `CampfireDesktopApp()` hosts `CampfireApp` inside a `dragAndDropTarget` that accepts dropped files; links open through `java.awt.Desktop`. `CampfireViewModel.handleKeyEvent(...)` is wired into the window's `onKeyEvent` by `:app:desktop`: desktop has no back gesture, so Escape dismisses whatever is open on top of the app, pops the back stack, clears the Songs search query on the root screen, or closes the app. What is open on top is `visibleDialog` plus `isAnyOverflowMenuOpen` (`components/OverflowMenu.kt`): a window key handler runs before Compose turns Escape into a back event, so an Escape consumed here would pop the back stack behind a dialog, a sheet or a menu instead of closing it.
- `iosMain/ui/CampfireIosApp.kt` — `CampfireIosApp(urlOpener, filePicker, filesToImport)` hosts `CampfireApp`. Takes the URL opener and the file picker as parameters so the module stays free of UIKit. Back navigation (including the swipe back gesture) is handled by Navigation 3 in `CampfireApp`.
- `wasmJsMain/ui/CampfireWebApp.kt` — `CampfireWebApp()` hosts `CampfireApp`; links open in a new tab and files dropped anywhere on the page are imported.

Everything else is `commonMain`:

- `ui/CampfireViewModel.kt` — a lifecycle `ViewModel`. Exposes `StateFlow`s derived from `GetScreenDataUseCase` (`stateIn(viewModelScope, WhileSubscribed)`), the grouped song list (`songGroups`, section headers computed here so the UI never needs `NormalizeTextUseCase`), `setlistsWithSongs`, `visibleDialog`, and the Navigation 3 `backStack` (`SnapshotStateList<CampfireDestination>`). The theme and the language come from a separate `GetUserPreferencesUseCase` rather than from `ScreenData`, so they reach the screen without waiting for the library scan. Intent handlers are non-suspend and launch in `viewModelScope`; the ones that write to the library go through `launchLibraryChange`, which turns a write that failed into a `Message.OperationFailed` snackbar instead of an uncaught exception that would take the app down on Android. A state is `asEagerState` whenever its first value is acted on rather than merely shown (`syncState`, which the Android shell stops the sync service from; `allSongs`, which the details screen picks its opening page from) — a `WhileSubscribed` state hands its subscriber the initial value for one frame first. Those `asState` states forget their last value the moment they stop (`replayExpirationMillis = 0`), since the initial value is what each of them means by "nothing has been worked out yet": kept, the song list would be entered on the answer worked out before a library change its screen was away for, which is exactly what a first sync is — it fills the library from the settings screen, and the list then opened on "Your library is empty" while the settings screen next to it already counted the songs. The search and the grouping run over `searchableSongs`, the library with every title and artist normalized once, rather than normalizing per keystroke. Each entry of `setlistsWithSongs` carries the place it has in its setlist, the missing files included, so the numbers a setlist is read by are its own order rather than a count of the rows that could be drawn. `updateSongFileName` is the one intent that changes a song's identity: the use case under it follows the references on disk, and what is left here are the two places the old name lives in memory — the text read from the file, and the back stack entries opened on it, which are rewritten rather than popped so that a song renamed from the details screen is still the song being read. Tagging a song (`setSongTag`) rewrites the file through `SetChordProTagUseCase` rather than touching the list entry, so the tag is in the song wherever that song goes; the tag *filter* is a user preference instead, since it is about this device's view of the library. The languages of a song work the same way (`setSongLanguages`, `toggleLanguageFilter`), except that the whole set is written at once, since the picker asks about all of them before it is closed. Every entry reports `transition.isRunning` through `ReportNavigationTransition`; a back stack change that interrupts a running transition bumps `navigationGeneration`, which goes into the entry metadata so the new scene never equals the one the transition started from. Without this, reversing an in-flight transition (e.g. going back right after opening a song) sends Navigation 3 down its "predictive back cancelled" path, which cannot handle an interrupted animation and leaves the UI stuck halfway. The three top level screens keep their scroll position here too (`ScrollPosition`, `components/ScrollPosition.kt`, read back by `rememberRetainedLazyListState` / `rememberRetainedLazyGridState`): Navigation 3 throws away everything an entry remembered as the entry leaves the back stack, and selecting a tab rebuilds that stack around the destination that was picked, so the songs screen — the one screen that sits at the bottom of every one of those stacks — used to be the only one that came back where the user left it.
- `ui/CampfireApp.kt` — the root composable used by every platform shell: theme, language preference, adaptive chrome (`NavigationBar` under 600dp, `NavigationRail` above — see `components/WindowSize`; the filter side panel is decided by the screens themselves, see `hasRoomForSidePanel`), the `Scaffold` + `NavDisplay`, `CampfireDialogs`, the snackbars for import and export results (queued with a running number, because two identical results in a row are the same object and an effect keyed on the message alone would never show the second), and the collection of `filesToImport`. `SyncNotificationEffect` only ever reports "nothing to show" after it has shown something: reported on the first frame of every composition it would reach the Android shell as "stop the service" whenever the app was opened onto a run already going in the background. It also rescans the library when the app is resumed, but only where the folder is one somebody else can edit (`libraryLocation != null`, i.e. iOS and desktop): on Android the library is app-private, and on the web `ON_RESUME` fires on every tab focus while OPFS cannot change behind the app's back. That resume, the read the app starts with and the action in the settings screen are the only three things that ever re-read the library: the songs screen has neither a pull to refresh nor a refresh button, because the library is the app's own and a list that is already up to date has nothing to pull for. All `NavDisplay` transitions are defined in this file and shared by every platform (the desktop default would be none): tab switches fade through with a small slide, pushing/popping `SongDetails` slides horizontally with a parallax (Material motion scheme springs), and `predictivePopTransitionSpec` follows the predictive back gesture (Android) / edge swipe (iOS) with linear specs. `SongEditor` is the exception and always moves vertically, up when it is opened and down however it is left, the predictive gesture included: it is presented as a modal over the song rather than as another card of the deck, which is what its Close button says as well. `CampfireDestination.SongEditor.isContentKey` is how the specs recognize it, since a scene only exposes content keys. `navigationTransition` serves both `transitionSpec` and `popTransitionSpec` and decides push vs. pop from the scene depth itself: Navigation 3's own detection is wrong when a back stack change interrupts a running transition (it would animate the pop with the push spec, leaving the invisible outgoing screen covering the list and swallowing clicks for the rest of the animation). Deeper scenes get a higher z-index. The rail and bottom bar are hidden on the details and editor screens; bars and side panels animate with expand/shrink using the same spatial spec so the content reflows fluidly. The chrome and the screens are laid out together by `NavigationChromeScaffold`, a `SubcomposeLayout` that measures the rail (or the bar) and only then composes the screens, with its thickness already known: that size is Material's to decide, and reporting it back as state from the laid out chrome arrives one layout pass too late, so the app's first frame would be composed as if the window held no chrome at all — the screens covering the rail and the lists settling their column counts for the full width, all of it laid out again a frame later. It costs no layer that was not there already, since the window size used to come through a `BoxWithConstraints`, which is the same thing. The chrome is placed under the screens and `placeRelative`d, so the rail sits on the start edge the screens are inset from. Nothing is drawn at all until the preferences have been read (`arePreferencesLoaded` — *read*, not read successfully, so a failed read opens the app in the defaults rather than never, and it only ever turns on, since what it gates is the whole of `CampfireContent` and everything remembered under it): they decide the palette and the language, and the window would otherwise open on the system's guess at both and correct itself a frame later, in an accent color and a language the user did not choose. That frame is not a fleeting one — on a cold start the second frame is several hundred milliseconds behind the first — and the wait costs nothing but the frame that would have been wrong anyway. What the window holds meanwhile is `LaunchScreen`, the app's mark on the theme's background, which is also what stays on screen while that first composition runs: it says nothing the preferences have not answered yet, carrying no text and drawn in a neutral rather than in the accent color. It is a Compose screen rather than a desktop one for a reason — a window held back with `visible = false` until the app is ready deadlocks, since Compose Desktop has no frame clock while no window is on screen, so the composition never advances to the point of asking to be shown. The other three platforms open on a startup screen of their own and never see it: Android's system splash, iOS's launch storyboard and the loading screen in the web build's `index.html`. Each of those is taken away by the first frame the app draws, and that frame is the launch screen rather than the app — so the two that can be held are told when to stop instead, through `CampfireApp`'s `onAppReady`, which fires two frames after the real content is composed (`withFrameNanos` resumes while its own frame is still being assembled, so the frame after it is the first one that is certainly drawn). `CampfireWebApp` answers it by calling `window.campfireReady`, which is what fades the page's loading screen out and finishes its progress bar; `CampfireActivity` answers it by letting a pre-draw listener through, which is what postpones the first frame and with it the system's handover. iOS's storyboard is the system's to dismiss, so there the launch screen is what covers the gap, as on the desktop.
- `ui/navigation/CampfireDestination.kt` — `NavKey`s: `Songs`, `Setlists`, `Settings` (top level), `SongDetails(songFileNames, setlistFileName, initialIndex)` and `SongEditor(fileName, shouldStartInsideFirstSection)`, the last of which also answers `isContentKey` so that `CampfireApp`'s transitions can pick the editor out of a scene. Top level selection resets the stack to `[Songs, tab?]` so back always returns to Songs. Songs and setlists are addressed by **file name** everywhere, which is their identity on disk.
- `ui/screens/settings/SyncSettings.kt` — the sync section of the settings screen, driven entirely by `SyncState`: an invitation to connect, or the account with what the last run did and the two things one can do about it. A build with no sync credentials has an empty `viewModel.syncProviders` and says so, rather than offering a button that cannot work. A finished run is reported as a success with the exact local date and time it happened (`kotlinx-datetime`, order and separators from a string resource so each language places them itself), never as a count of what moved.
- **Performance mode** (`UserPreferences.isPerformanceModeEnabled`, the switch at the very top of the settings screen, above its first section heading, since it is what decides what the rest of that list is still allowed to do) is the one preference that reaches every screen rather than one of them, so `CampfireViewModel` exposes it as `isPerformanceModeEnabled` on its own and each screen collects that instead of reading it out of the preferences. It is read only mode for the app while it is being played from: the two "New" buttons, the per-song menu (and the long press that opens it on touch), the actions menu of a setlist header, the drag handle, the overflow menu and the swipe a setlist row reorders and removes itself by, the "Add to setlist" action, the tag and language chips of the song details header and the transposition stepper all leave, which is also every way into the editor — the screen stays reachable by nothing. What is left is what a song is read with: the search, the sorting, the tag and language filters, the text size, lyrics only mode and the rescan, none of which change a file. The settings screen is the exception and keeps every row it has, since it is where the mode is switched back off; the two library actions there are disabled rather than hidden, the way the chord spelling is under lyrics only mode. Files the operating system hands over ("open with", a share, a drop) are still imported: that is not a tap that can happen by accident.
- `ui/screens/` — one package per destination (`songs`, `setlists`, `settings`, `songDetails`, `songEditor`). The setlists screen lists every song a setlist names, whatever the song filters are set to: those narrow a view of the library, while a setlist is the list somebody wrote down (`CampfireViewModel.setlistsWithSongs`, read from `ScreenData.unfilteredSongs`). What its controls ask instead is the order the setlists come in and whether the archived ones are among them — off by default, since that is what archiving one is for. An archived setlist is marked by the icon in its header pill — which fades in and out with the archiving rather than arriving between two frames, since the menu that archives one hangs from the other end of that very pill — and comes after the rest whatever the order, and a screen whose every setlist is archived says so rather than claiming there are none. Screens own their `TopAppBar` (which handles the status bar inset) and get a `contentPadding` for the bottom/horizontal insets from the outer scaffold so lists scroll edge to edge. Empty and error states are their own composables and animate in and out like everything else, so nothing appears or disappears abruptly while the library is still loading. Every lazy list in the app animates its items into place through `listItemAnimation` (`components/ListItemAnimation.kt`) rather than through `Modifier.animateItem()` directly, because there are two occasions it has to be left off. The song and setlist lists only animate once the library has arrived whole: the first read publishes what it has put together as it goes, so a list fills up in several batches and animating those would have it rearranging itself while the app is still opening. `rememberHasLoadedLibrary` is what draws that line, and it is an effect rather than `!isLoading` read directly, since the last and largest batch lands in the very composition that goes false. Every list, the settings one included, also leaves the animations off for as long as it is being scrolled: a lazy list moves the animation state of each item on screen by the distance the list was scrolled, and at the ends of the list — where a fast scroll asks for more than there is left to give — that distance is the one that was asked for rather than the shorter one that was actually scrolled, which lands the item far outside the list and then animates it back. What that looks like is one row sliding in from off screen while every other row is already still, most visibly the first row of the settings list after it is flung back to the top. Nothing is lost by it, since an item animation is there to narrate a change of the list's contents and the contents do not change under a finger. The one exception is a setlist being rearranged (`isRearranging`), where the contents change under the finger and the list scrolls itself as the dragged row reaches an edge, so the rows it passes have to keep sliding out of its way rather than snapping for as long as that scroll lasts.
- `ui/components/` — Material 3 list items (`SongListItem`, `SectionHeader`, `SwitchListItem`, `CheckboxListItem`, ...; a song listed inside a setlist carries its place in that setlist as a number in the leading slot, laid out over a fixed width so the titles stay on one keyline while a drag renumbers the rows it passes; `DragHandle` is the grip at the far end of such a row, after the overflow button and narrower than it, sitting on the keyline the app bar's own actions sit on — `ListItem` insets its trailing slot further than `TopAppBar` does, so every row's trailing controls are moved back onto that line (`ListItemActions`), which is what holds the end of a row and the end of the bar above it to one edge — an icon rather than an `IconButton` because the caller is what makes it draggable and because the width it gives up that way is empty space around an icon rather than anything that can be pressed), `SearchField` (`SearchBarDefaults.InputField`), `SegmentedChoice`, `ColorChoice` (the theme colors as discs rather than as names, wrapping instead of scrolling so none of them hides behind a gesture; the two whose color is not what picks them out — the app's own and the system's — carry an icon, which the check replaces while they are selected. The selected one is ringed in its own color, because a mark in the middle of a disc is read as what that color *is* once some of them carry an icon, so the selection has to sit where an icon never can), `SongActions` (the per-song menu: edit, "Update file name" where the file is named something other than what its metadata would name it (`Song.canUpdateFileName`, which is also why the entry is absent from most songs), add to setlist, export, share where the platform has one, delete; the add to setlist entry carries the setlists tab's star, filled where the song is already in a setlist and outlined where it is not - `CampfireViewModel.songFileNamesInSetlists` - which the song details app bar's button answers the same way, crossfading between the two), `SetlistActions` (the per-setlist menu behind the overflow button of its `SectionHeader` pill: rename, duplicate, archive or unarchive, export, delete - more than a pill has room for as buttons, and all but one of them lead somewhere else anyway), `OverflowMenu` (the dropdown behind every overflow button - the song and setlist menus and the editor's revert - which is also what counts the open ones, since a menu keeps that inside the composition and the desktop Escape handler is outside it), `ImportProgress`, `SongsControls` (sort + filters) and `SetlistsControls` (the setlists' own order, and whether the archived ones are shown), each used both as side panel and bottom sheet; `ControlsSidePanel` is the panel itself, taking whichever of the two as its content, spanning the full height next to the screen's app bar column (not below the bar) and handling the top inset itself. `SongListItem` names the key the song sounds in next to the artist rather than next to the title, which is the longest thing on the row and the one that must never be pushed out of sight, in the accent color the song details header keeps for what is played: `{key}` moved by the file's own `{transpose}` and by the transposition of the listing it is read in (`CampfireViewModel.renderKey`), which is why one song is in one key on the songs screen and in another inside a setlist that transposed it. It is worked out from the metadata the library scan already read rather than by parsing the file, since a list holds the whole library and none of its lyrics. A song with no chords says "Lyrics only" in that place instead, and a song that names no artist starts the line with the note itself. Whatever stands there is crossfaded rather than swapped, since it changes under the reader: a transposition renames the key and lyrics only mode empties the place altogether. Lyrics only mode empties the place altogether — no key, and no "Lyrics only" either, since that marker only tells one song from another while the others are showing chords — the way the mode takes the transposition control off the viewer. The song list has priority over the panel: `hasRoomForSidePanel` only shows it when at least three `ListColumns` columns still fit beside it (~1400dp of screen width), otherwise the same controls open in a bottom sheet from an app bar action.
- `ui/components/Languages.kt` — what a language is called, and the only part of the language feature the app ships: `LANGUAGE_CODES` (the ~620 codes the picker offers — ISO 639-1 plus the three letter ones 639-1 never covered, since no browser will enumerate languages) and `languageLabel(code)` / `languageName(code, appLanguageCode)`, which ask the platform for the name in the language the app is set to — `currentLanguage` is Compose state, so a chip follows the settings screen without a restart — and capitalize it, since CLDR writes `angol` rather than `Angol`. The English name stands in where the app's own language has none (CLDR thins out fast past the first few hundred languages, and a picker that lost a row when the app was switched to Hungarian would be worse), and only a code no platform can name at all is shown in capitals as the file wrote it. `pickableLanguages` is the picker's list: what can be named, ordered by that name through `NormalizeTextUseCase` so accents sort where a reader expects them — with the languages the library already sings in ahead of the rest, since the next song to be filed is far likelier to be in one of that handful than in any of the six hundred the library has never held. `SongLanguage.UNKNOWN` is the one code that is named from the string resources instead.
- `ui/components/Tags.kt` — `TagFlowRow` and `TagPill`, the one place a tag is drawn: under the artist in a song row (`SongLabels`, clipped to a single line, so a song filed under a dozen labels cannot make its row taller than the others), removable in the song details header, and as the suggestions of the tag dialog. `SongLabels` draws the song's languages there too, before the tags and each carrying the same mark the details header's chip does — a pill reading "Magyar" is otherwise a tag somebody typed, and a list gives no other way of telling the two apart. The filter chips of `SongsControls` are Material `FilterChip`s instead, since there the selected state is the point. `TagFilters` (in `Controls.kt`) shows the most used tags first and keeps the rest behind "Show all": the set of tags is whatever the library grew, and a hundred of them must not push the sorting mode off the panel. A selected tag is always among the visible ones, and the "any / every" choice only appears once two are on, because with one it would mean the same either way. `LanguageFilters` sits under it and is deliberately plainer — every language is shown (a library sings in a handful, not in a hundred) and there is no "any / every" question, since a song is never sung in every selected language at once. The whole group only appears once the library holds more than one language, counting the songs that declare none as one of them: below that there is nothing to choose between. Both groups draw the same `CountedFilterChip`.
- **A setlist row is reordered and removed in more than one way on purpose**, since neither gesture announces itself: the row drags from its handle (`draggableHandle`, which starts on the press) and also from a long press anywhere on it (`longPressDraggableHandle`), and a song leaves the setlist either by being swiped away or through the row's overflow menu. That menu is the song list's own `SongActions`, shown on touch platforms too rather than behind a long press like the song list's, because the long press is already spoken for by the drag. It offers no "remove" of its own: **one `Setlist assignments` entry covers both directions**, since the sheet it opens is every setlist with a box each, and unticking the box of the setlist the row is in is the swipe written as a list. Which box cannot be touched is `SetlistPicker.lockedSetlistFileName` - null here, and the setlist being read from on the song details screen, where unticking it would pull the page out from under the reader. An entry whose file has gone missing has no song to build those actions from, so it gets a bare `ActionsMenu` holding the one action that still means anything.
- **A drag is answered in the frame it is reported and written once when it ends.** The screen keeps the order the finger has put the rows in (`DraggedSetlist`, drawn through `SetlistWithSongs.rows`, each row numbered by the slot it sits in) and gives it up only once the library agrees, so nothing snaps back while the write is round tripping. `CampfireViewModel.reorderSetlist` then writes that order in one go, dealing the visible songs back into the slots visible songs occupied so that entries the filters hide keep their places. Writing per move instead worked each one out from a `setlists` value the previous move had not reached yet, which is what made a quick drag jump.
- `ui/dialogs/Dialogs.kt` — `CampfireDialogs` renders whatever `visibleDialog` asks for: the import conflicts dialog (the names an import would land on that are already taken by something else, with keep both / replace / skip and a cancel that leaves the library untouched — one answer for the whole batch, since the batch it exists for is an archive of hundreds; the plan it answers lives in the view model, because the answer can arrive long after the screen the import was started from), new song, new setlist and duplicate setlist `AlertDialog`s (a copy is named before it is made rather than after, since two setlists may carry the same title and one nobody named would sit under the original's),  the song language picker (every ISO code with a search over the names and the codes — including the codes a file may spell a language with rather than the one the library files it under, so that `HUN` and `hu-HU` both find Hungarian, which is `NormalizeLanguageCodeUseCase`'s job — the ones the song already declares held at the top for as long as the dialog is open — a row that reordered itself under the finger that just ticked it would be worse than a list that has to be scrolled — and one write when it is confirmed), rename setlist, delete song / delete setlist confirmations (the only way to delete either), the editor's unsaved changes and revert questions, and the song actions, controls, song display and setlist picker `ModalBottomSheet`s. The setlist picker is the one sheet that stays where it is while a dialog is up: its "New setlist" action renders the naming dialog on top of it from the picker's own state rather than through `visibleDialog` (which holds one dialog at a time), because the song goes into the new setlist as soon as it exists (`createSetlistWithSong`) and the picker is where that shows. Every dialog that holds a text field opens with the caret in it (`rememberFirstFieldFocusRequester`), which is what brings the keyboard up on a touch platform: each of them keeps that field as the first thing under the title, the language picker's search included, so there is only ever the one field to open on. `TextInputDialog` is the one place a dialog opens on text that is already there (a title being renamed, the name of a copy), and it holds a `TextFieldValue` rather than a `String` so that all of it starts out selected: that text is there to be replaced, so the first key typed has to write the new name instead of appending to the old one. A sheet that hides itself before running an action (`sheetState.hide()`) has to clear `visibleDialog` as well: Material's `ModalBottomSheet` only calls `onDismissRequest` for a swipe, a tap on the scrim or a back press, and a hidden sheet whose state is still set keeps its invisible modal layer over the screen, swallowing the next tap.
- `ui/theme/` — `CampfireTheme` (`MaterialExpressiveTheme`), which is driven by two independent preferences: `themeColor` picks the palette and `uiMode` picks its light or dark half. A change to either cross fades every color role from the scheme currently on screen to the new one with one progress value, so an interrupted switch continues from what is visible instead of jumping back. `ColorSchemes.kt` holds the `ColorSchemePair` (a palette's two halves, which always travel together) and `themeColorOptions()`, the single ordered list both the settings screen and `colorSchemePair()` read — a color the device cannot honor is simply not in it. `CampfireColorScheme.kt` is the app's own orange, hand-saturated over Material's tonal mapping of #F57C00; `MaterialColorSchemes.kt` is the rest, seven seeds run through Material's tonal spot mapping and pasted in, so a new color is a seed rather than forty values. `DynamicColorSchemePair.kt` is the one `expect`/`actual` here: on Android 12 and above it is `dynamicLightColorScheme` / `dynamicDarkColorScheme`, everywhere else null, which is what keeps the "System" swatch off the other platforms. Icons are XML vector drawables in `composeResources/drawable/`, loaded with `painterResource(Res.drawable.x)` and passed around as `Painter`.
- `ui/platform/LanguageNames.kt` — `languageDisplayName(code, inLocaleCode)`, four actuals over `java.util.Locale` (Android and desktop, one copy each since they are separate source sets), `NSLocale` and `Intl.DisplayNames`. Every platform carries the whole of CLDR for its own formatting, so asking it is both free and more complete than any list Campfire could keep up to date — a library may well hold a song in a language the app itself will never be translated into. Only the web actual can be missing at runtime, and it answers with null, which is the same thing an unknown code is.
- `ui/platform/Platform.kt` — `expect` declarations with one actual per platform: `isDesktopPlatform` (a song's actions are a menu in the row and in the app bar rather than a long press and a bottom sheet) and `libraryLocation` (a folder path on desktop, the Files app on iOS, null where the user cannot go and look — shown in Settings and used to decide whether resuming rescans) and `canAskForDonations` (false on iOS, where App Store guideline 3.1.1 lets nothing but an in-app purchase lead to paying the developer, so the "Buy me a coffee" link in the About section only exists on Android, desktop and the web).
- `ui/platform/AppUpdate.kt` / `ui/AppUpdateGate.kt` — what the store the app came from has to say about a newer build of it, which is only ever something on Android: Play is the one store of the four with an API for this (the App Store has none, and asking Apple's public lookup endpoint instead would be the second thing in the app that reaches the network). `AppUpdateGate` wraps the whole app inside `CampfireApp`, so the hint and the blocking screen are in the theme and the language chosen *in the app*. The policy is the Play release's own `updatePriority` and nothing else: 2–3 is a dismissible offer of a flexible update, 4–5 a screen the app cannot be used past. That screen is drawn *over* the app rather than in place of it, so an update that turns out not to install leaves the library where the user was. None of it shows up in a build Play did not install, which answers every check with an error. See the Updates section of the root `CLAUDE.md`.
- `ui/platform/LibraryPersistence.kt` — `requestLibraryPersistence()`, asked once from `CampfireApp` as the app starts and read back by the settings screen. Three platforms answer `GUARANTEED` without doing anything, since their library is in a file system of their own; the web actual calls `navigator.storage.persist()`, which is what stops a browser short of space from evicting the origin's storage — and with it the only copy of the user's library. The answer is cached, because the settings screen asks the same question again and the browsers that decide by asking the user must only ask once. A refusal is shown in the Library section instead of the location the other platforms have there, since a library that may be evicted is worth one line and an export.
- `ui/platform/BackgroundSync.kt` — `SyncNotifier`, provided by each shell through `LocalSyncNotifier` the way `FilePicker` is. A sync run already outlives the screen that started it, but on a phone that is not enough: Android stops a process nobody can see and iOS suspends one, so each shell has to tell its platform that something is going on. `CampfireApp` drives it from the sync state and resolves the strings, so the notification is in the language chosen *in the app*; a notification built from Android resources would follow the system's instead. Desktop and the web provide nothing, because neither needs anything.
- `ui/platform/FilePicker.kt` — the interface every shell provides through `LocalFilePicker`: `pickFiles`, `saveFile`, and `shareFile` with `canShare` saying whether sharing is a different thing from saving on this platform (it is on Android and iOS; on desktop and the web the menu shows "Export" alone).
- `ui/components/FastScroller.kt` — the only scrollbar in the app, on the song list: a draggable thumb with a 48dp touch target that only covers the thumb (other touches reach the list) and, only while the thumb is pressed, an animated bubble with the letter of the section at the top. Scroll position is estimated from the average visible item size. Visible on every platform for as long as the list is scrollable. That target is far wider than the thumb and runs down the edge the song rows keep their overflow button on, so the button is the one of the two that moves: the song list, alone among the lists, insets it by `FAST_SCROLLER_CLEARANCE`. Programmatic scrolls bypass nested scroll, so `KeepTopAppBarInSync` (in `CampfireTopAppBar.kt`) corrects the app bar's overlap state from the list.
- `ui/theme/Language.kt` — `ApplyLanguagePreference` maps the user preference to the generated `AppLocale` and sets `currentLanguage`, which every `stringResource` call observes.
- `composeResources/values[-hu]/strings.xml` — all UI strings. The `com.hyperether.localization` Gradle plugin turns them into Kotlin string tables (`build/generated/compose/resourceGenerator/kotlin/commonCustomResClass`, package `com.pandulapeter.campfire.presentation.localization`): `StringsDefault`, `StringsHu`, `AppLocale`, `currentLanguage`, `LocalizedStrings` and the language-aware `stringResource` overloads. Adding a new `values-xx` folder needs a clean build so the plugin regenerates `AppLocale`. The plugin's `generateTranslateFile` task only declares the resources folder *path* as an input, so `build.gradle.kts` registers the `strings.xml` files as inputs too; without that, new strings render as "???" until a clean build.
- `ui/components/CampfireTopAppBar.kt` — every screen's app bar: pinned scroll behavior plus an animated shadow/tint once content scrolls underneath (screens apply `nestedScroll(scrollBehavior.nestedScrollConnection)`). A screen with more controls than one row holds puts the rest in `bottomContent`, which is drawn inside the same surface (the editor's toolbar), so the whole bar tints and lifts as one. The section headers of the lists are raised pills (`SectionHeader`) for the same reason. They are ordinary items that scroll away with their section; clicking one scrolls back to the start of that section (`animateScrollToKey`, which looks the header's index up by its key, since an ordinary item is not told its own).
- `screens/songDetails/SongLyrics.kt` — renders the `ChordProSong` the parser produced (sections, chorus recall, the three comment styles, tabs in a monospace font, grids, the metadata header). Tablature is a run of lines inside a section rather than a section of its own (see `:chordpro`), so the lines of a section are grouped before they are drawn: each run of `ChordProLine.Tab` becomes one sideways scrolling block, because its columns only line up while they are measured together, and everything else is laid out line by line around it. A paragraph that holds nothing *but* one of the two still gets the default "Tab" / "Grid" heading, since that is a bare `{start_of_tab}` standing on its own and it named itself before; one with lyrics around the run is an ordinary paragraph and heading it would be a lie. Lyrics-only mode drops the tab and grid lines the way it drops the chords, since neither says anything without them, and a section left with nothing that way is dropped whole rather than leaving its heading behind. The header carries the song's languages and tags — one chip for the languages however many there are, which opens the picker, then each tag removable and an "Add tag" chip that opens the suggestions dialog — and then every other directive the editor can insert, since one that is written but never shown is one the user cannot check: the capo, the tempo and the time on an accent coloured line (what is read off the page while playing), the composer, lyricist, album, year and duration on a quieter one under it (what is only ever looked up). The title, the subtitle, the artist and the key are the ones that are deliberately not repeated, since the bar has all four — the subtitle in parentheses after the title (`ChordProMetadata.displayTitle`, which is how a song is named everywhere in the app), and the key inside the transposition control, which is the only reason to look at it. The editing chips are passed in and are absent in the editor's preview, where the file is under the caret and a chip writing into it from the side would be editing text that has not been saved, and in performance mode, which takes every way of writing to a file out of the app. Lyrics are split into sections and flowed into columns by `SongSectionsLayout`. It uses the *fewest* (and therefore widest) columns the song still fits the screen with, so the vertical space is used and the lyrics wrap as little as possible: the candidates are evaluated from the sections' intrinsic heights (the winner is the only width they are measured at, and a candidate that does not fit jumps straight to the smallest count that could), column widths are clamped to 384–560dp scaled by `fontScale` and the block is centered. Songs that do not fit at any count get as many columns as the width allows. `SongDetailsScreen` has to pass the height available without scrolling (`availableHeight`, from a `BoxWithConstraints` around the scrolling content), since inside the `verticalScroll` the layout only sees infinite height. Sections are distributed with a dynamic program that minimizes the columns' squared deviation from the ideal height — a greedy fill leaves every column short of the target and dumps all the accumulated slack on the last one. Section headers are the same raised pills as the song lists' section headers, scrolling with their section and hanging into the left padding so their text keeps the content's keyline; choruses are drawn on a raised card instead and keep a plain label (in the pills' `primary` text color), the other sections are indented to match the card's content. Sections are never split and animate between layouts with `animateBounds` inside a `LookaheadScope`. Two settings reach in here: `isLyricsOnlyModeEnabled` drops the chords (and with them the tab and grid sections, and the transposition control, which would have nothing left to act on), and `isHorizontalSectionFlowEnabled` fills the columns in rows across the page the way the systems of sheet music are read instead of column by column. Both apply to the editor's preview as well, since it renders the same `SongLyrics`.
- `screens/songDetails/SongDisplayControls.kt` / `FontScaleGestures.kt` — the transposition and text size steppers (`fontScale` in the view model, persisted in `UserPreferences.fontScale` with a debounce because a pinch changes it every frame). Each stepper is a tonal pill (`surfaceContainerHighest`, `CircleShape`) around its two buttons and the value, so that two of them side by side still read as two controls; the app bar uses a shorter variant of it (`isCompact`, which also lowers `LocalMinimumInteractiveComponentSize` to match the smaller buttons), the sheet keeps the 48dp touch targets. Expanded windows show the steppers inline in the app bar; narrower ones get a single "display options" action that opens the `SongDisplayControls` bottom sheet, so the bar never crowds. `Modifier.fontScaleGestures` handles pinch (damped with an exponent, so it is slow and precise) and Ctrl / Cmd + scroll wheel in the initial pointer pass and consumes them, leaving one-finger scrolling and plain wheel scrolling to the content.
- `screens/songDetails/SongKeyboardShortcuts.kt` — `Modifier.songKeyboardShortcuts` reads the song details screen with the arrow keys: Up and Down scroll the song, Left and Right step to the previous and the next song of the setlist. That is a keyboard on the desktop and the web, and it is also a page turner pedal paired with a phone or a tablet, which is exactly what those send. The screen takes focus as it opens, since nothing on it would otherwise ever be focused and a key event only travels along the focus path, and the handler sits in the preview pass rather than the bubbling one so that it sees the event wherever inside the screen the focus has since moved to (an app bar button that was clicked, the scrolling content itself) and so that the scrolling container underneath never interprets an arrow of its own. Consuming all four takes two dimensional focus traversal away from this screen, which is the trade — the keys are worth more to a reader here than they are to Tab, which still traverses everything. Left and Right are left unconsumed at the ends of the setlist and when there is a single song to read. The scroll step is a tenth of the viewport animated linearly over roughly the interval a held key repeats at, so one press is a smooth nudge and a held key scrolls at a steady pace instead of stuttering between steps; it reaches the scroll state of the page that is current, which `SongDetailsScreen` hoists out of `SongDetailsPage` for it (each page scrolls on its own, and the current one hands its state up).
- `screens/songEditor/` — the raw ChordPro editor, presented as a modal: it comes up from the bottom and its app bar starts with Close rather than Back. The whole bar is one surface (`CampfireTopAppBar`'s `bottomContent`), so everything in it tints and lifts together as the text scrolls underneath, and it is four rows deep on a narrow window:
  - the **title row**, holding what acts on the file — undo/redo from `TextFieldState.undoState`, Save, and an overflow menu;
  - a row with the **transposition stepper** and the **Edit / Preview / Split** choice. These two are together because they are the two controls here that do not write at the caret, which is why they are also the two that stay when the rest leaves. Split is only offered where two panes fit (`WindowSize.EXPANDED`) but is what the choice starts at, and a window that narrows only *shows* Edit instead of it, so widening the window again goes back to both panes. The choice is always drawn, including on a window wide enough that it has all three options, so that the stepper is never alone in a row of its own;
  - two rows of `EditorToolbar.kt`, a button for every directive `ChordProParser` understands and the app then shows, so that a format whose vocabulary only exists in its own documentation can be written without knowing it by heart. They are split into what writes what the song **is** (title, key, tempo — what a file opens with, usually filled in once) and, under it, what writes the **song** (chords, the seven sections the app has a name for, tablature and grids, comments), so the row being scrolled through is always the short one. Tab and Grid are a group of their own between the sections and the comments, because that is what they are: a display mode that opens inside a section rather than a section of its own.
  - Three kinds of directive are deliberately absent, all of them still read without complaint: `{new_song}`, since the editor only ever holds one song; `{new_page}` / `{column_break}`, since Campfire flows sections into columns at whatever size the window is and a hand written break would decide nothing; and `{transpose}`, which the renderer does add on top of the reader's own transposition but which the app has no reason to encourage — the details screen transposes what is being read and the editor's transpose action rewrites the chords themselves, and both of those say what they did, where a directive shifting every chord away from what the file spells out does not. The rows scroll horizontally rather than wrapping, and their buttons take no focus, or the keyboard would close under the toolbar on every tap and the insertion would land where the caret used to be. Everything in braces is inserted on a line of its own, which is the only way ChordPro reads it as a directive. The metadata row is the one that does not write at the caret at all: a directive describing the song is valid anywhere in the file and belongs in none of those places but the header, so `:chordpro`'s `ChordProHeader` picks the line (in the order the row itself lists them, and without moving anything the user has arranged their own way) and the caret follows it there, ready for the value. Those buttons also go out of reach once the file carries what they write — a song has one title and came out in one year — which leaves Tag and Language as the two that can be tapped again and again, since a song has as many of either as it carries; what the file declares is read from the text as it is typed, so a directive written by hand disables its button as well.
  - The stepper is the details screen's own `TextTranspositionControls`, except that transposing here rewrites the file rather than changing how it is read: there is no amount and nothing to reset to, so it shows the song's key, or a `?` where the file names none. Either a `{key}` or a chord is enough to enable it — a key says what the song is in and is worth moving before a chord has been written under it, and a chord chart with no key is still a chord chart. The title is `ChordProMetadata.displayTitle` over the text as it is typed and the line under it the artist, both from one `ChordProParser.summarize` call that also answers whether there is anything to transpose; the save state is the Save button's own enabled state and is not spelled out.
  - Export and Delete are not here: they belong to the song list and the viewer. Revert is, alone in the overflow menu and behind a confirmation (`DialogType.RevertChanges`) — a menu of one rather than a button of its own, because throwing away everything typed since the last save is not something to end up in by mistapping the button next to Save. It is answered by the screen rather than by the view model — the text goes back through the field's own editing, so a revert is one more step of the undo history instead of the end of it.
  - The screen itself is a `BasicTextField` over a `TextFieldState` (its own `scrollState`, never wrapped in a `verticalScroll` — that swallows the press that places the caret), an explicit Save action (and Ctrl / Cmd + S) which is the only thing that ever writes the file, and a live preview of the same `SongLyrics` the viewer uses, side by side where the window has the room for it and one at a time otherwise — and the insertion rows leave with the field they write into whenever the preview is the only pane showing. The text size preference reaches the preview and deliberately not the field: it is how large the lyrics are read from across a room, and the field holds the source of the file rather than the song (scaling it would also move the columns of a tab away from the width the monospaced font keeps them at). Lyrics only mode is the one preference that does not reach the preview at all: it is a way of reading a song, and a preview that hid the chords being typed opposite it would answer an edit with nothing. The two panes are `weight(1f)` and not `fillMaxSize()`: a `Column` measures a weightless child against an unbounded height, and a song longer than the screen then lays the field out past the bottom edge of it instead of scrolling inside it. `ChordProOutputTransformation` colours the text from `ChordProHighlighter`'s tokens in the viewer's own colours, so a chord looks like a chord on both sides of the divider. The screen reports the text to the view model as it is typed without saving it (`onEditorTextChanged`), which is what `hasUnsavedEditorChanges` is measured from: every way back out of a screen goes through `CampfireViewModel.navigateBack`, so that is where an editor with unsaved text is caught and the `UnsavedChanges` dialog (save / discard / cancel) is asked instead of popping. The draft is also what the dialog saves, which is why it lives in the view model rather than here - the answer can come after this screen is gone.
