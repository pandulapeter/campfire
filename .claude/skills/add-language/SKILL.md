# Adding a language to Campfire

One language per run. Everything below is required; a language missing any step is broken somewhere (a "???" string,
English system dialogs on iOS, an English loading screen on the web, a docs list that forgets it). The checklist is
enforced by `scripts/language.py`; run it, never skip it.

Romanian (`ro`) was added this way and is the worked example: when unsure how a step looks, look at how `ro` appears in
that file. Don't commit unless the user asks (then load the `commit-messages` skill). Load the `code-style` skill before
editing any `.kt` or `strings.xml` file.

`L=.claude/skills/add-language/scripts/language.py` below.

## 1. Ask for the language

If the request names no language, ask for one (AskUserQuestion, or a plain question). If it names several, take the
first, say the others need a run each, and carry on with that one only.

Settle these names now and use them everywhere:

| Name | Rule | Romanian |
|---|---|---|
| code | ISO 639-1 (639-2 only if no 639-1), lowercase, no region | `ro` |
| English name | as English writes it | `Romanian` |
| enum entry | English name, upper snake case | `ROMANIAN` |
| key suffix | English name, lower snake case | `romanian` |
| own name | the language's name for itself, capitalized as a picker shows it | `Română` |
| strings object | `Strings` + code capitalized (generated by the plugin) | `StringsRo` |

## 2. Preflight: stop if the language needs groundwork

Write a sample with **every letter of the language's alphabet in both cases, every diacritic, its quotation marks, and
any punctuation of its own**, then run:

```
python3 $L preflight <code> --sample "<sample>"
```

- **Exit 2 (`ABORT` lines): stop.** Make no changes. Tell the user that `<Language>` needs groundwork before it can be
  added, quoting each `ABORT` line, and what that groundwork is:
  - *fonts*: the app is set only in its bundled Inter and JetBrains Mono (Latin, Greek, Cyrillic); another script needs
    a font bundled for every platform, credited (root `CLAUDE.md` → Build), and chosen per language in `ui/theme`.
  - *right to left*: the layout, chord rows over lyrics, the editor, pagers, and the PDF have never run RTL.
  - *plurals*: the generated `LocalizedStrings.getPlural` picks only `one` (for 1) and `other`, so few/many languages
    (Russian, Polish, Czech, …) need Campfire's own plural selection first.
  - *code*: a regional variant, or a language the platforms name two ways (`id`/`in`, `he`/`iw`), needs
    `ApplyLanguagePreference` / `AppLocale.findByCode` taught to map it.
- **`NOTE` lines**: carry on, keep them for step 5's brief and the final report. If the note says the plural table
  does not know the language, apply its rule yourself and stop if it fails.
- **Exit 0**: carry on.

## 3. Wire the language into the app

Each item is checked by `wiring` in step 7.

1. `data/model/.../preferences/AppLanguage.kt`: add `<ENUM>("<code>"),` after the last language, before
   `SYSTEM_DEFAULT`.
2. Nothing in `presentation/.../ui/components/preferences/LanguageChoice.kt`: it lists every `AppLanguage`, sorted by
   code.
3. `.../preferences/AppLanguageNames.kt`: import `…presentation.resources.settings_user_interface_language_<suffix>` and
   add `AppLanguage.<ENUM> -> Res.string.settings_user_interface_language_<suffix>` to the `when`.
4. The name key in **every existing** `composeResources/values*/strings.xml`, right after the last
   `settings_user_interface_language_<language>` line: `<string name="settings_user_interface_language_<suffix>">` with
   the language's name in that file's language (English `Romanian`, Hungarian `Román`). The new file gets the own name.
5. `tools/screenshots/src/main/kotlin/.../screenshots/Shot.kt`: import `…presentation.localization.<StringsXx>` and add
   `AppLanguage.<ENUM> -> <StringsXx>.strings[key]` to `string(key)`. It compiles only after step 6's regeneration.
6. iOS (`app/ios/iosApp`), so system UI speaks the language and Settings offers it:
   - `iosApp/Info.plist` and `ShareExtension/Info.plist`: `<string><code></string>` at the end of
     `CFBundleLocalizations`.
   - `iosApp/<code>.lproj/InfoPlist.strings`: copy `hu.lproj/InfoPlist.strings` (license header and comment kept) and
     translate the `NSMicrophoneUsageDescription` English text from `iosApp/Info.plist`.
   - `ShareExtension/<code>.lproj/Localizable.strings`: copy `en.lproj/Localizable.strings`, change its comment to
     "The share extension's <Language> strings. Keep in step with en.lproj.", translate every value. Add `<code>.lproj`
     to the "Keep … in step" sentence of `en.lproj`'s comment.
   - `iosApp.xcodeproj/project.pbxproj`, four places; copy each `hu` line and change `hu` to the code:
     two `PBXFileReference` lines (`path = <code>.lproj/Localizable.strings` and `path = <code>.lproj/InfoPlist.strings`),
     their IDs added to the `Localizable.strings` and `InfoPlist.strings` `PBXVariantGroup` children, and `<code>,` in
     `knownRegions`. New IDs: the same 24 hex digits as the neighbours with a new ending; `grep -c <ID>` must be 0 first.
     Afterwards `plutil -lint` the project, both plists, and both new `.strings` files.
7. Web, `app/web/src/wasmJsMain/resources/index.html`: add a `<code>: { … }` block to `TEXTS` with every key the
   `en` block has, translated, and the code to the `navigator.language` alternation (`/^(hu|ro|<code>)\b/i`).

8. Windows, `app/desktop/AppxManifest.xml`: add `<Resource Language="<code>-<region>" />` (lowercase, the region the
   language's main Partner Center locale has, `de-de`) after the last one. Partner Center then asks for a listing in it,
   which step 5's store listings provide.

Nothing else per platform: Android needs no locale config (the language is chosen in the app), the desktop runtime
already carries every locale (`jdk.localedata`). The release notes in the language come from its own `whats-new <code>`
block, which prepare-release writes for every `values-*` folder.

## 4. Docs that list the languages

Add the language to each list, in the house style (Oxford comma, the language last):

- root `CLAUDE.md` → Strings: `values[-hu|-ro|-<code>]/strings.xml`.
- `presentation/CLAUDE.md`: the summaries bullet's "(English, Hungarian, …)".
- `app/web/CLAUDE.md`: "Texts follow `navigator.language` (…)".
- `app/ios/CLAUDE.md`: the `Localizable.strings` (…) and `CFBundleLocalizations` (…) code lists.
- `documentation/store-listings/*/en.md` (all four stores): "English, Hungarian, …, switchable inside the app", and the
  same line in every other language's file (`documentation/store-listings/*/<language>.md`), named in that language.

Rewrap any line pushed past ~120 columns.

## 5. Translate the strings

`presentation/src/commonMain/composeResources/values/strings.xml` is ~1,300 lines; translate it in parallel chunks.

1. Split it: `python3 $L split <scratchpad>/<code>`. It prints the chunks (`en_N.xml`) and where each translation goes
   (`xx_N.xml`).
2. Fill in the glossary below for the language before anything is translated, so every chunk uses the same words.
   Decide the address: the app speaks to the user informally, second person singular (Hungarian "te", Romanian "tu");
   keep that unless it is rude in the language's software, and say so in the report if you changed it.
3. Start one subagent per chunk, all in one message, `model: "opus"`, `subagent_type: "general-purpose"`,
   `run_in_background: true`, each with the brief below filled in.
4. Read each agent's list of doubts. Look up how each doubtful key is used (`grep -rn "Res.string.<key>\b"` in
   `presentation/src/commonMain/kotlin`) and fix the ones that are wrong once the file is joined.
5. Join: `python3 $L join <code> <scratchpad>/<code>` writes `values-<code>/strings.xml`.
6. The store listings: one subagent (`model: "opus"`) writes `documentation/store-listings/<store>/<code>.md` for each
   of the four stores, translated from `<store>/en.md` the way the other languages' files are (read one first: which
   fields each holds, the English headings and rules note, the locales line, keywords researched rather than
   translated, the app's own words from the new `strings.xml`), and runs `.github/scripts/check_store_listings.py` and
   `.github/scripts/store_listings.py --check` (every field the release writes is there).
   Its Play title and App Store name become the website's title in the language: if the website already has the
   language (`i18n/<code>.json` of the CampfireWebsite repository), set its `Campfire: Songbook &amp; Chords` entry to
   that name and run its `stamp.py`; if not, say in the report that the website's translation should use it.
7. If the preflight noted that 0 takes the singular, give each plural that `values-fr` gives a `zero` item one too, on
   a line of its own after `<plurals>`: the plurals a count of 0 can reach ("Aucune chanson").

bridge, scale, key (musical), capo, transpose, tempo, time signature, beat, metronome, tuner, tuning, instrument, tools
(the nav item holding Metronome, Tuner, Chords, and Scales), tab (tablature), fret, neck, settings, features,
preferences, layout, page, pedal, auto-scroll, sync, shared link, share, import, export, save, cancel, delete, done,
close, back, create, edit, undo, redo, clear (a search field), archive, cover art, search, filter, sort, duplicate,
rename, file name, folder, onboarding, what's new, demo library, microphone, major, minor, and the mode names (Ionian,
Dorian, Phrygian, Lydian, Mixolydian, Aeolian, Locrian, harmonic, melodic, pentatonic, blues).

## 6. Check the strings

```
python3 $L strings <code>
```

Fix every `ERROR`. Read every `WARN`: an English-identical string is fine only for names and symbols, and a `one` item
without its count is fine only where "1" reads badly. The script checks the keys, their order, comments, placeholders,
plural items, characters no bundled font can draw, and right-to-left text.

## 7. Build and verify

```
./gradlew spotlessApply :presentation:generateTranslateFile --rerun-tasks
python3 $L wiring <code> <EnglishName>
./gradlew desktopTest :tools:screenshots:compileTestKotlin :app:desktop:compileKotlin spotlessCheck
./gradlew :tools:screenshots:test
python3 .github/scripts/check_license_headers.py && python3 .github/scripts/check_sizes.py
```

The `--rerun-tasks` regeneration is required: the plugin adds the new `AppLocale` entry and `<StringsXx>` only on a
clean run. `wiring` must print `OK`; each `ERROR` names the file and what is missing. A file pushed past a size limit is
split by cohesion as the `code-style` skill says, never left over the limit.

If this run had to touch a place `wiring` does not check, add it to `check_wiring` in `scripts/language.py` and to step
3 or 4, so the next language gets it too.

## 8. Report

Tell the user, in a few lines: the language added and its own name in the picker; what was wired (code, iOS, web,
docs); the test and check results; the translation choices worth a native speaker's look (address, key terms, the
agents' doubts you kept); every preflight `NOTE` as a known limitation; and that nothing was committed. Also tell them to
add the language's listing by hand, once, in every console (Play Console, App Store Connect for iOS and for the Mac, and
Partner Center), with its screenshots, before the next release: the release writes every listing's text from the files
but creates none, so a store without the language fails the release on the missing listing. If the store spells the
language other than by its ISO 639-1 code (Play's `iw` for Hebrew) or splits it by script (`zh-CN`, `zh-TW`), it needs
an alias in `.github/scripts/store_listings.py`'s `ALIASES`, and a line in `test_store_listings.py`'s `STORE_LOCALES`.
